    Si vous avez déjà tapé quelque chose dans le champ de recherche d'un site WordPress et attendu trois secondes pour obtenir des résultats à côté de la plaque, vous savez de quoi je vais parler.

    La recherche native de WordPress est le parent pauvre du CMS. Elle fonctionne, au sens où elle renvoie quelque chose. Mais dès que votre site dépasse la centaine de contenus, elle devient lente, et ses résultats sont classés dans un ordre qui n'a pas grand-chose à voir avec la pertinence.

    J'ai fini par écrire mon propre bloc Gutenberg de recherche instantanée, adossé à un index MySQL dédié. Le plugin est téléchargeable en bas de cet article. Mais avant ça, je voudrais vous expliquer pourquoi j'ai fait ces choix, parce que c'est là que se trouve la partie intéressante.

    Le vrai problème n'est pas dans le thème

    Commençons par regarder ce que WordPress fait réellement quand vous cherchez « travaux en entreprise ».

    WP_Query prend votre terme et génère, en simplifiant à peine, une requête de cette forme :

    SELECT * FROM wp_posts
WHERE (post_title LIKE '%travaux%'
    OR post_excerpt LIKE '%travaux%'
    OR post_content LIKE '%travaux%')
  AND (post_title LIKE '%entreprise%' OR ...)

    Le problème tient dans un seul caractère : le % placé avant le terme recherché.

    Un index MySQL fonctionne comme l'index d'un livre, trié alphabétiquement. Si je vous demande de trouver tous les mots commençant par « trav », vous allez directement à la bonne page. Si je vous demande tous les mots contenant « trav » n'importe où, vous devez lire le livre en entier.

    C'est exactement ce que fait MySQL ici. Un LIKE préfixé par % n'est pas indexable : le moteur parcourt l'intégralité de la table wp_posts, révisions et brouillons compris. Sur un blog avec 500 articles et leurs révisions, ça peut représenter plusieurs milliers de lignes lues à chaque frappe.

    Et le classement ? Il n'y en a pas. WordPress trie par date. Un mot présent trois fois dans le titre pèse exactement autant qu'une occurrence perdue au fond d'un article de 2019.

    Pourquoi je n'ai pas pris un plugin existant

    La réponse habituelle est Relevanssi ou SearchWP. Ce sont de bons outils, et si vous cherchez une solution qui marche sans réfléchir, allez-y sans hésiter, c'est le choix rationnel.

    De mon côté je voulais trois choses qu'ils ne me donnaient pas ensemble :

    • une recherche instantanée intégrée comme un bloc Gutenberg, administrable avec les outils natifs de l'éditeur ;
    • la maîtrise complète de la pondération, pour décider moi-même qu'un mot dans le titre vaut six fois un mot dans le corps ;
    • aucune dépendance JavaScript à compiler, parce que je voulais pouvoir déposer le dossier en FTP et que ça fonctionne.

    Et accessoirement, je voulais comprendre comment ça marche sous le capot. C'est souvent la meilleure raison de coder quelque chose soi-même.

    La décision structurante : une table d'index dédiée

    MySQL sait faire de la recherche plein texte depuis longtemps, avec les index FULLTEXT et l'opérateur MATCH ... AGAINST. Contrairement au LIKE '%mot%', c'est indexé, donc rapide.

    La question devient : où mettre cet index ?

    Option 1 : sur wp_posts directement

    C'est tentant, une ligne de SQL suffit :

    ALTER TABLE wp_posts ADD FULLTEXT INDEX ft_search (post_title, post_content);

    J'ai écarté cette option. Modifier le schéma d'une table du cœur de WordPress, c'est s'exposer à des surprises à chaque migration d'hébergeur, chaque restauration de sauvegarde, chaque import. Et surtout, ça ne règle qu'une partie du problème : pour afficher un résultat il faut encore l'URL, la vignette, et pour un produit WooCommerce sa référence. Autant d'allers-retours supplémentaires vers wp_postmeta.

    Option 2 : une table à moi

    C'est celle que j'ai retenue.

    La table {prefixe}_search_index est dénormalisée : elle contient une ligne par contenu publié, avec le titre, le corps nettoyé, les termes de taxonomies, l'extrait, l'URL et l'URL de la vignette. Tout ce qu'il faut pour afficher un résultat.

    Le gain est direct : une recherche complète, c'est une seule requête SQL. Aucun passage par wp_posts, aucun par wp_postmeta. Sur mon site, une recherche répond en quelques millisecondes.

    Le coût, c'est qu'il faut maintenir cet index à jour. Le plugin s'en charge via les hooks save_post, deleted_post et set_object_terms.

    Trois pièges que j'ai découverts en route

    Voilà la partie que j'aurais aimé lire avant de commencer.

    1. dbDelta() ne sait pas créer d'index FULLTEXT

    dbDelta() est la fonction WordPress qui crée et met à jour les tables de plugins. Elle est pratique, mais elle ne comprend pas la syntaxe FULLTEXT KEY. Elle l'ignore silencieusement, ou pire, elle la mange à moitié.

    La solution est de créer la table sans les index plein texte, puis de les ajouter par des ALTER TABLE explicites, en vérifiant d'abord qu'ils n'existent pas déjà :

    $exists = $wpdb->get_var(
    $wpdb->prepare("SHOW INDEX FROM {$table} WHERE Key_name = %s", $name)
);

if ($exists === null) {
    $wpdb->query("ALTER TABLE {$table} ADD FULLTEXT INDEX {$name} ({$columns})");
}

    2. Il faut un index par combinaison de colonnes

    Celui-là m'a coûté une bonne heure.

    Pour pondérer, je voulais écrire ceci :

    SELECT post_id,
       (MATCH(title) AGAINST ('travaux*' IN BOOLEAN MODE) * 6)
     + (MATCH(extra) AGAINST ('travaux*' IN BOOLEAN MODE) * 3)
     + (MATCH(body)  AGAINST ('travaux*' IN BOOLEAN MODE))
       AS score
FROM index_table
WHERE MATCH(title, extra, body) AGAINST ('travaux*' IN BOOLEAN MODE)
ORDER BY score DESC

    MySQL refuse, avec un message qui ne dit pas grand-chose au premier abord :

    Can't find FULLTEXT index matching the column list

    La règle est stricte : chaque MATCH() a besoin d'un index dont la liste de colonnes correspond exactement. Un index composite sur (title, extra, body) ne couvre pas un MATCH(title) seul. Il faut donc quatre index :

    Le piège vicieux, c'est que $wpdb avale l'erreur SQL par défaut. Vous n'obtenez pas d'exception, juste un tableau vide et une recherche qui ne trouve jamais rien.

    3. Les mots courts sont invisibles

    InnoDB ignore les mots plus courts que innodb_ft_min_token_size, qui vaut 3 par défaut. Sur un hébergement mutualisé comme o2switch, vous ne pouvez pas modifier ce réglage.

    Concrètement : chercher « en » ou « ne » ne renverra jamais rien via MATCH. Le plugin détecte le cas et bascule sur un LIKE 'terme%' sur le titre. Ce n'est pas indexé, mais sur une table d'index étroite ça reste peu coûteux.

    Dans le même registre, MySQL n'a pas de racinisation. « chaussure » ne trouve pas « chaussures ». Je compense avec un joker sur chaque terme en mode booléen : chaussure*.

    Le front sans une ligne à compiler

    La partie visible utilise l'Interactivity API, arrivée avec WordPress 6.5 et bien affinée depuis. Elle permet d'écrire des blocs interactifs avec des directives dans le HTML, un peu à la manière d'Alpine.js, sans embarquer React côté visiteur.

    Le rendu est déclaré côté serveur :

    <input
    type="search"
    data-wp-on--input="actions.onInput"
    data-wp-bind--aria-expanded="context.isOpen"
/>

    Et la logique dans un module JavaScript natif. WordPress fournit l'import map, donc l'import fonctionne sans bundler :

    import { store, getContext, withSyncEvent } from '@wordpress/interactivity';

    Deux détails valent le détour.

    Le debounce sans setTimeout partagé

    Chaque frappe déclenche une requête potentielle, et il faut éviter d'en envoyer une par caractère. L'astuce classique est un setTimeout qu'on annule, mais avec plusieurs blocs sur la même page ça devient bancal. J'utilise plutôt un compteur stocké dans le contexte :

    const seq = ++ctx.seq;

yield new Promise( ( resolve ) => setTimeout( resolve, 220 ) );

if ( seq !== ctx.seq ) {
    return; // une frappe plus récente est arrivée, on abandonne
}

    Le même compteur sert après la réponse du serveur. C'est ce qui empêche une requête lente d'écraser un résultat plus récent, un bug pénible à reproduire et facile à éviter une fois qu'on y a pensé.

    withSyncEvent() est obligatoire depuis WordPress 6.8

    Dès qu'une action asynchrone touche à l'objet event, il faut l'envelopper. Sans lui, vous récupérez un avertissement de dépréciation et un comportement qui changera dans une version future.

    La leçon que j'ai apprise à mes dépens

    J'ai livré la première version avec une commande WP-CLI pour construire l'index, documentée dans le README.

    Puis je l'ai installée sur mon propre site, et la recherche ne renvoyait rien. Zéro résultat, aucune erreur. J'ai regardé la requête SQL, les index, le mode booléen.

    La cause était bête : l'index était vide, tout simplement. L'activation créait la table mais ne la remplissait pas, et je n'avais pas SSH activé sur cet hébergement pour lancer la commande.

    Une fonctionnalité indispensable placée derrière un outil que l'utilisateur n'a pas forcément, ce n'est pas une fonctionnalité. C'est un bug avec de la documentation.

    La version que vous téléchargez ajoute donc un écran Outils → Recherche instantanée qui affiche le nombre de contenus indexés, l'état des index FULLTEXT, les réglages InnoDB de votre serveur, un bouton de reconstruction et un champ de test. Et l'activation planifie une indexation initiale via WP-Cron.

    Ce que le plugin ne fait pas

    Autant être clair sur les limites, parce qu'elles sont réelles.

    • Pas de tolérance aux fautes de frappe. Si votre visiteur tape « entrprise », il n'aura rien. MySQL ne sait pas faire de recherche approximative. C'est la frontière la plus nette.
    • Pas de racinisation intelligente. Le joker rattrape les pluriels simples, mais pas les formes irrégulières ni la conjugaison.
    • Pas de synonymes, pas de facettes, pas de recherche sémantique.

    Si l'un de ces points est bloquant pour votre projet, ne cherchez pas à contourner : passez sur un moteur dédié comme Meilisearch ou Typesense. Ils gèrent tout ça nativement, se mettent en route en une après-midi, et Meilisearch tourne avec une centaine de mégaoctets de RAM.

    J'ai d'ailleurs isolé toute la logique de requête dans une seule classe, SearchRepository. Si vous voulez brancher Meilisearch derrière, c'est le seul fichier à remplacer. Le bloc, l'endpoint REST et l'indexeur restent inchangés.

    Téléchargement et installation

    Le plugin demande PHP 8.2 et WordPress 6.8 minimum. Il fonctionne avec MySQL comme avec MariaDB.

    Télécharger le plugin (.zip)
    1. Téléchargez l'archive et décompressez-la dans wp-content/plugins/
    2. Activez le plugin depuis l'administration
    3. Allez dans Outils → Recherche instantanée et cliquez sur « Reconstruire l'index »
    4. Ajoutez le bloc Recherche instantanée où vous voulez, y compris dans un en-tête via l'éditeur de site

    L'écran d'administration vous dira immédiatement si quelque chose cloche. Si le compteur affiche zéro contenu indexé, c'est là qu'il faut regarder en premier.

    Le code est commenté en français, y compris aux endroits où j'explique pourquoi j'ai fait un choix plutôt qu'un autre. C'est fait pour être lu et modifié.

    Pour aller plus loin

    Quelques pistes si vous voulez l'adapter :

    • Le filtre erwan_live_search_extra_parts permet d'ajouter n'importe quel contenu à la colonne pondérée : champs ACF, métadonnées personnalisées, tout ce qui a du sens dans votre contexte.
    • erwan_live_search_post_types restreint ou étend les types de contenu indexés.
    • La navigation au clavier dans la liste de résultats n'est pas implémentée. C'est un bon exercice si vous voulez vous familiariser avec l'Interactivity API.

    Si vous l'installez et que quelque chose coince, écrivez-moi. Et si vous trouvez un quatrième piège que je n'ai pas vu, je suis preneur.
